# Дизайн кода

Адаптировано из mattpocock/skills (MIT), `skills/engineering/codebase-design/SKILL.md`.

Проектируй глубокие модули. Много поведения за маленьким интерфейсом, на чистом шве, тестируемо через этот интерфейс. Цель в рычаге для вызывающих, локальности для тех, кто сопровождает, и тестируемости для всех.

## Словарь

Используй эти термины ровно так. Не подменяй их словами «компонент», «сервис», «API», «граница». Весь смысл в одном языке.

**Модуль.** Все, у чего есть интерфейс и реализация. Масштаб не важен, это функция, класс, пакет или срез через несколько слоев. Не говори юнит, компонент, сервис.

**Интерфейс.** Все, что вызывающему нужно знать, чтобы правильно пользоваться модулем. Сигнатура типов, а еще инварианты, порядок вызовов, режимы ошибок, обязательная конфигурация и характеристики производительности. Не говори API или сигнатура, это слишком узко и про один только уровень типов.

**Реализация.** То, что внутри модуля, его код. Это не то же самое, что адаптер. Бывает маленький адаптер с большой реализацией (репозиторий на Postgres) и большой адаптер с маленькой реализацией (фейк в памяти). Про шов говори «адаптер», в остальных случаях «реализация».

**Глубина.** Рычаг на интерфейсе. Сколько поведения вызывающий или тест получает на единицу интерфейса, которую ему пришлось выучить. Модуль **глубокий**, когда за маленьким интерфейсом много поведения, и **мелкий**, когда интерфейс почти так же сложен, как реализация.

**Шов** (термин Майкла Фезерса). Место, где можно поменять поведение, не правя код в этом месте. Это то, где живет интерфейс модуля. Где поставить шов, отдельное решение, независимое от того, что за ним. Не говори граница, это слово занято bounded context из DDD.

**Адаптер.** Конкретная вещь, которая удовлетворяет интерфейсу на шве. Описывает роль (какой слот занимает), а не содержимое.

**Рычаг.** Что вызывающие получают от глубины. Больше возможностей на единицу выученного интерфейса. Одна реализация окупается в N местах вызова и M тестах.

**Локальность.** Что сопровождающие получают от глубины. Изменения, баги, знание и проверка собраны в одном месте, а не размазаны по вызывающим. Починил один раз, починено везде.

## Глубокий и мелкий

**Глубокий модуль** это маленький интерфейс и много реализации.

```
┌─────────────────────┐
│ Маленький интерфейс │  ← мало методов, простые параметры
├─────────────────────┤
│                     │
│ Глубокая реализация │  ← сложная логика спрятана
│                     │
└─────────────────────┘
```

**Мелкий модуль** это большой интерфейс и мало реализации. Его избегаем.

```
┌─────────────────────────────────┐
│       Большой интерфейс         │  ← много методов, сложные параметры
├─────────────────────────────────┤
│  Тонкая реализация              │  ← просто передает дальше
└─────────────────────────────────┘
```

Проектируя интерфейс, спроси себя.

1. Можно ли уменьшить число методов?
2. Можно ли упростить параметры?
3. Можно ли спрятать внутрь больше сложности?

## Принципы

1. **Глубина это свойство интерфейса, а не реализации.** Глубокий модуль внутри может состоять из маленьких, подменяемых частей, просто они не входят в интерфейс. У модуля бывают **внутренние швы** (закрытые, для его собственных тестов) и **внешний шов** на интерфейсе.
2. **Тест удаления.** Представь, что модуль удалили. Сложность исчезла, значит он был прослойкой. Сложность проступила в N вызывающих, значит он себя окупал.
3. **Интерфейс и есть поверхность для тестов.** Вызывающие и тесты пересекают один и тот же шов. Хочется тестировать мимо интерфейса, значит у модуля, скорее всего, не та форма.
4. **Один адаптер это гипотетический шов, два адаптера это настоящий.** Не вводи шов, пока через него ничего не меняется.

## Тестируемость

Хороший интерфейс делает тесты естественными.

1. **Принимай зависимости, не создавай их.**

   ```typescript
   // Тестируется
   function processOrder(order, paymentGateway) {}

   // Тестируется плохо
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **Возвращай результат, а не делай побочный эффект.**

   ```typescript
   // Тестируется
   function calculateDiscount(cart): Discount {}

   // Тестируется плохо
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **Маленькая поверхность.** Меньше методов, меньше нужно тестов. Меньше параметров, проще подготовка теста.

## Связи

1. У **модуля** ровно один **интерфейс**, поверхность для вызывающих и тестов.
2. **Глубина** это свойство **модуля**, измеренное относительно его **интерфейса**.
3. **Шов** это место, где живет **интерфейс** модуля.
4. **Адаптер** стоит на **шве** и удовлетворяет **интерфейсу**.
5. **Глубина** дает **рычаг** вызывающим и **локальность** сопровождающим.

## Отклоненные трактовки

1. **Глубина как отношение строк реализации к строкам интерфейса** (у Оустерхаута). Поощряет раздувать реализацию. Мы меряем глубину рычагом.
2. **«Интерфейс» как ключевое слово `interface` в TypeScript или публичные методы класса.** Слишком узко. Здесь интерфейс включает все, что вызывающий должен знать.
3. **«Граница».** Занято bounded context из DDD. Говори **шов** или **интерфейс**.
