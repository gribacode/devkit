# devkit: личный плагин Claude Code для фуллстека React + NestJS

Дата: 2026-10-03
Статус: дизайн согласован, ждет ревью спека

## Зачем

Набор команд и хуков, который работает одинаково в своих проектах, на работе (self-hosted GitLab `192.168.10.102`) и в контрибьютах в чужие публичные репозитории (GitHub). Закрывает пять задач:

1. Ревью кода по принципам сильных инженеров.
2. Описание MR или PR по практикам сильных команд.
3. Отработка незакрытых комментариев ревью с короткими ответами без ИИ-текста.
4. Учет активности и отчет за день строго по времени.
5. Уведомления, защита от опасных действий, автоформат и проверка типов.

## Решения, принятые при обсуждении

1. Форма поставки это личный плагин в отдельном git-репозитории `~/Documents/code/devkit`, подключается как локальный marketplace, позже публикуется в личный GitHub. Причина: хуки в `~/.claude/settings.json` перезаписывают Orca и herdr, а хуки плагина живут в его `hooks/hooks.json` и не затираются.
2. Команды это `commands/*.md`, а не skills. Их вызываю я явно, модель не должна запускать ревью или отчет сама.
3. Хуки на Python 3 только со стандартной библиотекой (`/usr/bin/python3`). Без uv, без Node, чтобы не зависеть от fnm.
4. Похожие команды из `~/frontend/.claude/commands` (`branch-review`, `fix-review`, `worklog`, `worklog-report`, `commands`) переезжают в плагин. Специфичные (`dev`, `daily-standup`, `stage-commit`, `hunk-review`, `branch-explain`, `branch-summary`, `new-command`, `new-doc`, `notes-add`) остаются в frontend.
5. Уведомления только macOS через `osascript` со звуком.
6. `/review-reply` ничего не постит в MR, только выдает текст ответов.
7. Включены все четыре хука валидации: Bash-сторож, защита секретов, формат после правки, tsc на Stop.

Команды ссылаются на файлы в `refs/` через `${CLAUDE_PLUGIN_ROOT}/refs/...` и читают их по необходимости. `refs/` лежит в корне плагина, а не в `commands/`, потому что подкаталоги `commands/` Claude Code регистрирует как команды. Подстановка `${CLAUDE_PLUGIN_ROOT}` в тексте команд работает, так делает официальный плагин `code-modernization`.

## Общие правила текста (`refs/style.md`)

Применяются ко всему, что команды пишут человеку, кроме кода в обратных кавычках и commit message.

Русский:

1. без тире и дефиса как знака препинания в середине предложения (дефис в составном слове и в диапазоне времени `09:30-10:45` можно)
2. без буквы е с точками
3. без точки с запятой, двоеточие только в `файл:строка`
4. без ИИ-шных вводных и оценок: конечно, отличный вопрос, давайте разберем, в целом, стоит отметить, важно понимать, отлично, качественно
5. без эмодзи
6. числа цифрами

Английский:

1. без длинного тире
2. без «This PR», «I hope», «Great catch», «Thanks for the review!»
3. без слов comprehensive, robust, seamless, enhance, leverage, delve

Перед выводом команда проверяет свой текст поиском по запрещенным символам.

## Команды

### `/review [база | ссылка на MR/PR]`

Только чтение, ничего не постит.

Сбор контекста:

1. Аргумент пуст: база из `git symbolic-ref --short refs/remotes/origin/HEAD`, иначе ветка, от которой ответвилась текущая.
2. Аргумент ветка: она база.
3. Аргумент ссылка: дифф через `glab mr diff` (GitLab, хост берется из ссылки) или `gh pr diff` (GitHub). Ветку не переключает.
4. `git diff <база>...HEAD` и `--stat`, `AGENTS.md` и `CLAUDE.md` репозитория, профильные `docs/`, вызывающий и вызываемый код вокруг изменений.
5. По расширениям и импортам в диффе подгружает нужные чеклисты: React, NestJS, общий.

Принципы (`refs/review-principles.md`), каждый пункт подписан источником:

1. Google eng-practices. Порядок взгляда: дизайн, функциональность, сложность, тесты, имена, комментарии, документация. Планка: изменение улучшает кодовую базу, а не идеально.
2. Илья Климов. Ревьюим смысл, форматирование оставляем линтеру. У каждого замечания серьезность и «почему». Не уверен, задай вопрос вместо вердикта.
3. Тимур Шемсединов. Антипаттерны из HowProgrammingWorks: магические числа, мутация аргументов, скрытые побочные эффекты, лишние абстракции и наследование, God object, протекание фреймворка в предметную логику. Бизнес-логика не в контроллерах и резолверах.
4. George Hotz. Каждая строка это пассив. Минимальный дифф, никаких абстракций на будущее, рефакторинг не меняет поведение, простое лучше умного.
5. Conventional Comments. Метки серьезности.
6. feiskyer. Каждая находка перед выводом перепроверяется по реальному коду, неподтвержденные выкидываются.

Чеклисты:

1. React: зависимости эффектов, устаревшие замыкания, `key`, производное состояние в `useState`, гонки загрузки данных, лишняя и недостающая мемоизация, a11y, error boundaries, ссылка на скилл `vercel-react-best-practices`.
2. NestJS: DTO с `whitelist`, guards на резолверах, N+1 в field resolvers (DataLoader), транзакции Prisma, утечка `password` без `select`, `ConfigService` вместо `process.env`, опасные миграции.
3. Общий: схема GraphQL и сгенерированные типы не разошлись, секреты, мертвый код, отладочные вызовы, локализация, комментарии по регламенту из `branch-review`.

Вывод:

1. Первая строка: вердикт одной фразой, можно мержить или что мешает.
2. Находки по серьезности, около 10, хвост мелочей одним блоком.
3. Находка: метка и `файл:строки`, одно предложение что не так и почему плохо, третья строка `Фикс.` только если решение неочевидно.
4. Метки: `[баг] [безопасность] [архитектура] [сложность] [API] [тест] [док] [стиль] [мертвый код]`.
5. Все чисто: одна фраза.

### `/pr [база] [ru|en]`

Только чтение, ничего не создает.

1. Шаблон репозитория: `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE/`, `.gitlab/merge_request_templates/`, требования `CONTRIBUTING.md` (changeset, DCO, чекбоксы). Есть шаблон, заполняет ровно его.
2. Язык: аргумент, иначе язык последних 10 MR/PR или коммитов, чужой публичный репозиторий всегда английский.
3. Структура без шаблона (`refs/pr-structure.md`):
   1. Заголовок `type(scope): subject`, до 72 символов, императив. Номер задачи из ветки, если в репо так принято.
   2. Зачем. Проблема или контекст 1 по 3 предложения, ссылка на задачу (`Closes #123` или ключ JIRA).
   3. Что сделано. 3 по 7 пунктов про поведение.
   4. Как проверить. Конкретные шаги или команды.
   5. Скриншоты. Место под них, только если менялся UI.
   6. На что смотреть. Миграции, breaking changes, новые env, неочевидные решения. Только если реально есть.
4. Дифф больше 400 строк без lock-файлов и сгенерированного: предложение разбить.
5. Вывод: заголовок и тело одним блоком кода плюс готовая строка `glab mr create` или `gh pr create`.

### `/review-reply <ссылка на MR/PR>`

1. Ссылки нет: спросить одной строкой.
2. GitLab (любой хост из ссылки): `glab api --hostname <хост> projects/<id>/merge_requests/<iid>/discussions`, брать `resolvable && !resolved`, пропускать `system`.
3. GitHub: `gh api graphql`, `reviewThreads` с `isResolved=false`. Нет `gh`, подсказать `brew install gh && gh auth login` и остановиться.
4. Ветка MR не совпадает с текущей: сказать и остановиться.
5. Нет незакрытых тредов: сказать одной строкой и остановиться.
6. По каждому треду: суть простым языком 1 по 2 предложения, решение (правим, не правим с причиной, вопрос ревьюеру). Код смотреть текущий, не цитату.
7. Показать план и ждать ок. До ок код не трогать.
8. После ок внести правки только в то, о чем треды.
9. Вывод по каждому треду: строка `файл:строка, автор`, под ней ответ для вставки. Одно предложение, первое лицо, прошедшее время, язык как у комментария. Пример: «Поправил, обернул запись в транзакцию.» или «Оставил так, значение уже проверяет валидатор в DTO.»
10. Не коммитит, не пушит, не резолвит, ничего не постит.

### `/worklog [заметка | созвон HH:MM-HH:MM тема]`

Логика текущей команды из frontend без изменений по сути:

1. Пишет строку `- HH:MM-HH:MM (45м) [tag] описание` в `~/.claude/worklog/<дата>.md`, создает файл с `# <дата>` если нет.
2. Пустой аргумент: чекпоинт, начало это первое событие в activity после конца последней записи.
3. Теги: `[dev] [review] [fix] [docs] [call] [meeting] [talk] [misc]`.

### `/report [дата | вчера]`

Источники по приоритету:

1. `~/.claude/worklog/<дата>.md`: созвоны и чекпоинты.
2. `<дата>.activity.tsv` (новый формат) и `<дата>.timeline.tsv` (старый, колонки iso, событие, cwd, ветка фронта, ветка бэка, тема).
3. `git reflog --date=iso` и `git log --all --since --until` автора из `git config user.email` по каждому репозиторию из колонки `repo` (для старого формата: корень git по `cwd`).

Расчет времени делает `scripts/worklog_blocks.py`, а не модель, чтобы цифры были детерминированными. Команда берет из его JSON время и длительности как есть и пишет только суть блоков. Правила расчета:

1. Работа это промежутки от `UserPromptSubmit` до следующего `Stop`.
2. Пауза между `Stop` и следующим промптом до 15 минут тоже работа, длиннее это перерыв.
3. Созвон из `.md` перекрывает активность в своем диапазоне.
4. Соседние промежутки одной задачи склеиваются в блок. Задача это номер из ветки (`ABC-123`), иначе имя репозитория.
5. Блоки короче 10 минут склеиваются с соседом по времени.
6. Границы округляются до 5 минут.

Вывод строго по времени:

```
Отчет за 2026-10-03

09:30-10:45  1ч 15м  DEV-5279 поправил счетчик комментариев в карточке сделки
10:45-11:15  30м     дейлик
11:15-13:00  1ч 45м  DEV-5279 развел комментарии сделки и коммуникаций

Итого 3ч 30м
```

1. Суть блока синтезируется из тем промптов и коммитов, шум выкидывается.
2. Первое лицо единственного числа: исправил, добавил, разобрался.
3. Нет `.md` за день: внизу строка «время восстановлено по активности».
4. Отчет дополнительно сохраняется в `<дата>.report.md`.

### `/check`

1. Менеджер пакетов по lock-файлу.
2. Пакеты монорепо, затронутые `git diff` от базы и рабочим деревом.
3. По каждому скрипты из `package.json`, какие есть: `lint`, `typecheck` или `tsc --noEmit`, `test`. Есть `schema.prisma`: `prisma validate`.
4. Короткая сводка падений и предложение фикса. Без ок не правит.

### `/agent-lint [путь] [--fix]`

`npx -y agnix <путь>` по текущему проекту, по умолчанию плюс `${CLAUDE_PLUGIN_ROOT}`. Сводка по ошибкам. `--fix` только по явному аргументу.

### `/commands`

1. Читает `${CLAUDE_PLUGIN_ROOT}/commands/*.md`, `~/.claude/commands/*.md`, `.claude/commands/*.md` текущего проекта. Имя файла это команда, `description` это суть.
2. Группы плагина: Ревью и MR (`review`, `pr`, `review-reply`), Время (`worklog`, `report`), Проверки (`check`, `agent-lint`), Справка (`commands`).
3. Ниже локальные команды проекта и пользователя отдельными группами.
4. Последней строкой активные хуки и их выключатели.

## Хуки

Общее для всех (`_common.py`):

1. Читают JSON из stdin, любые исключения глотают. Падение хука не ломает сессию.
2. Выключатели через env: `DEVKIT_ACTIVITY`, `DEVKIT_NOTIFY`, `DEVKIT_GUARD`, `DEVKIT_FORMAT`, `DEVKIT_TSC`. Значение `0` выключает.
3. Состояние сессии в `~/.claude/devkit/state/<session_id>.json`: время последнего промпта, список правленых файлов. Файлы старше 7 дней чистятся при `SessionStart`.
4. Поиск node: PATH, иначе `~/.local/share/fnm/aliases/default/bin`. Бинари проекта только из ближайшего вверх `node_modules/.bin`, `npx` с загрузкой не используется.

`hooks/hooks.json`:

| Событие | Матчер | Скрипт | Таймаут |
|---------|--------|--------|---------|
| SessionStart | | activity.py | 5 |
| SessionEnd | | activity.py | 5 |
| UserPromptSubmit | | activity.py, notify.py | 5 |
| Notification | | notify.py | 5 |
| PreToolUse | Bash | guard_bash.py | 5 |
| PreToolUse | Read\|Edit\|Write\|MultiEdit\|Grep | guard_secrets.py | 5 |
| PostToolUse | Edit\|Write\|MultiEdit | format_edit.py | 60 |
| Stop | | activity.py, stop.py | 120 |

### `activity.py`

1. Строка в `~/.claude/worklog/<дата>.activity.tsv`, при создании файла первой строкой заголовок `time event session repo branch topic`.
2. `repo` это `git rev-parse --show-toplevel` от `cwd` (пусто вне git), `branch` его текущая ветка. Таймаут git 2 секунды.
3. `topic` первая непустая строка промпта до 200 символов, табы и переводы строк заменены пробелом. Для не-промптов пусто.
4. Ничего не печатает, всегда exit 0.

### `notify.py`

1. `UserPromptSubmit`: записывает время старта в состояние сессии, уведомления нет.
2. `Notification`: уведомление всегда. Заголовок имя репозитория или папки, текст из `message` хука, звук `Glass`.
3. Отправка через `osascript -e 'display notification ...'`, кавычки экранируются. `DEVKIT_NOTIFY_DRYRUN=1` печатает в stderr вместо отправки.

### `stop.py`

1. `stop_hook_active` true: проверку типов пропустить, чтобы не уйти в цикл, дальше как в пункте 5.
2. Из состояния берет правленые `.ts`/`.tsx`, группирует по ближайшему `tsconfig.json`.
3. По каждой группе `tsc --noEmit -p <tsconfig>` из локального `node_modules/.bin`, таймаут 90 секунд. Нет tsc, группа пропускается.
4. Ошибки фильтруются по правленым файлам. Есть ошибки: stdout `{"decision":"block","reason":"<до 20 ошибок>"}`, уведомления нет. Список правленых не очищается.
5. Чисто: список правленых очищается. Если с последнего промпта прошло 20 секунд и больше, уведомление. Текст это начало последнего ответа ассистента из `transcript_path` (до 100 символов), иначе «Готово».
6. Таймаут tsc или любая ошибка: пропустить проверку, не блокировать.

### `guard_bash.py`

Блокирует exit 2, причина в stderr на русском с подсказкой «запусти сам через !». Список:

1. `rm` с `-r` и `-f` по `/`, `~`, `$HOME`, `*`, `..`, `.` целиком. Внутри проекта (`node_modules`, `dist`, конкретные пути) разрешено.
2. `git commit`, `git push`, `git reset --hard`, `git clean` с `-f`, `git checkout -- .`, `git restore .`. `git add` разрешен.
3. `prisma migrate reset`, `prisma db push` с `--force-reset` или `--accept-data-loss`, `DROP TABLE`, `DROP DATABASE`, `TRUNCATE`.
4. `sudo`, `chmod -R 777`, `curl` или `wget` с пайпом в `sh` или `bash`.
5. Чтение секретов через `cat`, `less`, `head`, `tail`, `source`, `.` по путям из правил `guard_secrets`.

Команда разбирается по сегментам `&&`, `||`, `;`, `|`, чтобы ловить опасное в цепочке.

### `guard_secrets.py`

Путь из `file_path` или `path`. Блок exit 2 для: `.env` и `.env.*` кроме `.example`, `.sample`, `.template`; `*.pem`, `*.key`, `*.p12`; `id_rsa*`, `id_ed25519*`; `credentials*.json`; `.npmrc`; всего под `~/.ssh` и `~/.aws`.

### `format_edit.py`

1. Файл в `node_modules`, `dist`, `build`, `.next`, `coverage` или сгенерированный (`*.generated.*`, `__generated__`): пропуск.
2. Расширения `js jsx ts tsx mjs cjs json css scss md`: `prettier --write`, таймаут 15 секунд.
3. Расширения `js jsx ts tsx mjs cjs`: `eslint --fix`, затем, если остались ошибки, exit 2 и до 20 строк ошибок в stderr. Предупреждения не блокируют. Таймаут 30 секунд.
4. `.ts`/`.tsx` добавляются в список правленых в состоянии сессии.
5. Нет prettier или eslint в проекте: молча пропуск.

## Тестирование

1. `tests/run.sh` с временным `HOME`, подает `fixtures/*.json` в каждый хук, проверяет exit code и вывод.
   1. guard_bash: блок `rm -rf /`, `rm -rf ~`, `git push`, `git commit -m x`, `prisma migrate reset`, `cat .env`. Пропуск `rm -rf node_modules`, `git add src`, `git status`, `cat .env.example`.
   2. guard_secrets: блок `.env`, `.env.local`, `id_rsa`. Пропуск `.env.example`, `src/env.ts`.
   3. activity: строка с заголовком появилась, колонок 6.
   4. stop: `stop_hook_active` дает exit 0 без вывода. Без правленых файлов тоже.
   5. notify: в режиме dryrun уведомление пишется в stderr, при ответе быстрее 20 секунд уведомления нет.
   6. format_edit: на временном проекте без node_modules молча exit 0.
2. `npx -y agnix .` по плагину без ошибок.
3. Ручная проверка после установки: `/commands` показывает список, уведомление приходит, строка в activity.tsv пишется, правка `.ts` с ошибкой типов блокирует Stop.

## Установка и перенос

1. `claude plugin marketplace add ~/Documents/code/devkit`, затем `claude plugin install devkit@devkit`.
2. После ручной проверки и отдельного подтверждения: удалить 5 команд из `~/frontend/.claude/commands` и хуки activity из `~/frontend/.claude/settings.json`, иначе события пишутся дважды. `~/.claude/worklog/activity-hook.py` оставить до конца переходного периода.
3. Позже: репозиторий на личный GitHub, установка через `/plugin marketplace add <github-user>/devkit`.
