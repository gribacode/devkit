# Углубление

Адаптировано из mattpocock/skills (MIT), `skills/engineering/codebase-design/DEEPENING.md`.

Как безопасно углубить группу мелких модулей с учетом их зависимостей. Словарь из `${CLAUDE_PLUGIN_ROOT}/refs/codebase-design.md`: **модуль**, **интерфейс**, **шов**, **адаптер**.

## Категории зависимостей

Оценивая кандидата на углубление, разложи его зависимости по категориям. Категория определяет, как углубленный модуль тестируется через шов.

### 1. В процессе

Чистые вычисления, состояние в памяти, никакого IO. Углубляется всегда. Слей модули и тестируй через новый интерфейс напрямую. Адаптер не нужен.

### 2. Локально подменяемые

Зависимости, у которых есть локальная замена для тестов (PGLite вместо Postgres, файловая система в памяти). Углубляется, если замена существует. Углубленный модуль тестируется с заменой, запущенной в тестах. Шов внутренний, порта на внешнем интерфейсе модуля нет.

### 3. Удаленные, но свои (порты и адаптеры)

Свои сервисы за сетью (микросервисы, внутренние API). На шве определи **порт** (интерфейс). Логикой владеет глубокий модуль, транспорт внедряется как **адаптер**. Тесты используют адаптер в памяти, прод использует адаптер на HTTP, gRPC или очереди.

Форма рекомендации. *«Определи порт на шве, сделай HTTP-адаптер для прода и адаптер в памяти для тестов. Логика останется в одном глубоком модуле, хотя развернута через сеть.»*

### 4. Настоящие внешние (мок)

Сторонние сервисы (Stripe, Twilio и подобные), которыми ты не управляешь. Углубленный модуль принимает внешнюю зависимость как внедренный порт, тесты подают мок-адаптер.

## Дисциплина швов

1. **Один адаптер это гипотетический шов, два адаптера это настоящий.** Не вводи порт, пока не оправданы хотя бы два адаптера (обычно прод и тест). Шов с одним адаптером это просто лишняя косвенность.
2. **Внутренние и внешние швы.** У глубокого модуля бывают внутренние швы (закрытые, для его собственных тестов) и внешний шов на интерфейсе. Не выставляй внутренние швы в интерфейс только потому, что ими пользуются тесты.

## Стратегия тестов. Заменять, а не наслаивать

1. Старые юнит-тесты мелких модулей становятся лишними, как только появились тесты на интерфейсе углубленного модуля. Удали их.
2. Новые тесты пиши на интерфейсе углубленного модуля. **Интерфейс и есть поверхность для тестов.**
3. Тесты проверяют наблюдаемый результат через интерфейс, а не внутреннее состояние.
4. Тесты переживают рефакторинг внутренностей, потому что описывают поведение, а не реализацию. Тест приходится менять при смене реализации, значит он тестирует мимо интерфейса.
